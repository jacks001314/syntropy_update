# v0.1.1 — BOM 的锚点是产品，插件可以推进

> 发布 2026-10-09 · Tag `v0.1.1` · 部署 `https://app.syntropy-lab.com`
> 口径见主仓库 `../Syntropy/docs/system-upgrade-method.md`；总体设计见 `docs/design.md`。

## 为什么要这一版

方法说明的规则 3 是「插件可以单独升级，产品不能」——插件各有版本号，可以随时单独发布并推进
BOM。但 v0.1.0 的实现把整份 BOM 判成不可变：同一 `(channel, productVersion)` 只要组件对不上
就报「请升产品版本号」。于是「插件单独升级」这句在服务端根本走不通，内容组件（templates /
skills）也永远进不了已经发过的渠道。

## 变更

- **`PublishDistribution` 的锚点从「整份 BOM」缩到「产品这一格」**：允许同一
  `(channel, productVersion)` 被重新发布，条件只有一个——BOM 里的 `product` 条目与已发布的
  那份是同一份发布（`ReleaseID` 与版本都相同）。产品自己换了仍然报 `ErrValidation`
  （请升产品版本号）。
- 推进 BOM 时保留 `CreatedAtMS`、刷新 `PublishedAtMS`，审计记 **`distribution.update`**
  （新建仍然是 `distribution.publish`）。
- 规则只在 `release.PublishDistribution` 一处实现：`bundle.Import` 不再自己判定 BOM 冲突，
  只把服务端的结果翻译成报告（`已推进 … 的 BOM（N 个组件）` / `已存在且一致，跳过`）。

## 配套（主仓库侧）

- 新增 `desktop_app/tools/content-archive.mjs`：把 `data/<组件>` 打成**确定性**的 `.tar.gz`
  （固定 mtime、条目按名字排序、gzip 头不带时间戳）。这不是洁癖：服务端按 sha256 判定
  「同一版本不可换字节」，而 CI 每次都是全新 checkout，系统 `tar` 打出来的字节每次都不同。
- 新增 `desktop_app/tools/content-release.json`：内容版本（`templates` / `skills` = `1.0.0`），
  源目录固定是仓库根 `data/<组件>`；`pnpm release:build` 自动打包进
  `dist/update-bundle/content/`，`pnpm release:publish` 与安装器走同一条命令。

## 验证

- 本仓库：`go build ./... && go vet ./... && go test -count=1 ./...` 10 个包全绿；新增
  `TestPublishDistributionAdvancesPluginsOnly`（插件推进成功 + 产品变更被拒）。
- 生产 `https://app.syntropy-lab.com`：`templates@1.0.0`（541 条目 / 197,211 字节）与
  `skills@1.0.0`（737 条目 / 1,419,696 字节）灌库，`stable/0.4.3` 的 BOM 由 3 个组件推进到
  **5 个组件**（审计 `distribution.update`，`createdAtMs` 不变、`publishedAtMs` 前进）；
  整份发布包重跑**全部 skipped**。
- 闭环：从线上 blob 取回两份归档，sha256 与 BOM 声明一致，用客户端解析器
  （`apps/desktop/src/main/updates/content-archive.ts`）解开后与仓库 `data/<组件>` 逐字节一致；
  `POST /v1/plan` 上报 product 0.4.2 / codex 0.159.0 / node-runtime 24.13.0 /
  templates 0.0.1 / skills 0.0.1，5 个组件全部给出 `upgrade`（内容组件审批 `auto`）。

## 升级注意

- 行为变化只影响「同一产品版本下 BOM 的组件集合变化」这一种情况：以前一律拒绝，现在「产品没动」
  就放行。产品换了的行为完全不变。
- 使用 v0.1.0 已部署的实例直接换二进制即可，数据格式没有变化。
