# v0.1.0 — 组件模型收敛为 5 行，发布只剩一条命令

> 发布 2026-10-09 · Tag `v0.1.0` · 部署 `https://app.syntropy-lab.com`
> 口径来自主仓库 `../Syntropy/docs/system-upgrade-method.md`（唯一的方法说明）；
> 本服务的总体设计见 `docs/design.md`。

## 这个版本解决什么

原来的受管清单是「一成员一组件」：`desktop` / `mbot` / `nbot` / `node-repl` / `app-server`
各自一行，一次版本变更要分别发五遍，容易漏发；发布方式有两套（本地手工搬文件，
CI 完全不碰升级服务）；服务端 CLI 又只能在本机数据目录上跑。这一版把三件事一次收敛：

1. **组件只有两类、清单只有 5 行**；
2. **产品只有一个版本号，只能整体升级**；插件各自有版本号，可以单独升级；
3. **发布只有一条命令**，本地与 CI 跑的是同一句。

## 变更

### 组件模型（破坏性）

受管组件由「一成员一组件」收敛为 5 个：

| 组件 | 类型 | 成员 / 制品 | 版本 |
| --- | --- | --- | --- |
| `product` | 产品 | `desktop` / `mbot` / `nbot` / `node-repl` / `app-server` 五个**槽位** | 产品版本（0.4.3） |
| `codex` | 插件 | 按 (os, arch) 的归档 `.tgz` | = Go SDK 的 `GeneratedCodexVersion`（0.160.0） |
| `node-runtime` | 插件 | 按 (os, arch) 的裸二进制 | 独立（24.14.0） |
| `templates` | 插件 | 平台无关目录归档 | 内容版本 |
| `skills` | 插件 | 平台无关目录归档 | 内容版本 |

- 旧组件名 `desktop` / `mbot` / `nbot` / `node-repl` / `app-server` 不再是受管组件，
  它们是 `product` 的**槽位**；产品里同一个 `(os, arch)` 会有多件制品，客户端按槽位选件。
- **制品键**由 `(releaseID, os, arch)` 变为 `(releaseID, slot, os, arch)`；管理面路由相应变为
  `PUT /v1/admin/releases/{id}/artifacts/{slot}/{os}/{arch}`，平台无关的组件用 `any/any`。
- 签名清单的制品条目新增 `slot` 字段。
- `browser-runtime` 从受管清单移除：当前没有生产者，等有产物再作为插件加入，不保留断链。

### 新增：远端灌库，发布不用再碰服务器

- 新增 `internal/adminclient`：实现 `bundle.Service` 的管理面 HTTP 客户端，
  于是「本地写数据目录」与「远端调 API」共用同一段 `bundle.Import`。
- `syntropy-update import-bundle` 新增 `-remote <url>` / `-token <token>`。
- 幂等语义不变：同一份输入重跑只跳过，同版本换字节直接报错。
- 修掉一个真实缺陷：`http.Transport` 发完请求会关闭请求体，而 `bundle.Import` 之后还要自己
  关那个文件，远端路径会冒 `file already closed`；客户端因此用「只读不关」的壳包一层请求体。

### 新增：按槽位选件

- `GET /v1/manifest`（桌面自更新）只挑产品里 `desktop` 槽位那一件。
- `GET /v1/components/{component}/manifest` 在 `component` 为空或为 `desktop` 时归一成
  `product`，旧调用不破。

## 兼容性

- 消费方需要桌面端 **0.4.3 或更高**：从该版本起按槽位选件、按 5 行组件上报库存。
- `GET /v1/distributions/{channel}/{productVersion}` 与 `GET /v1/distributions/latest?channel=`
  的响应结构不变，组件条目里新增 `slot` 字段。

## 验证

- 本仓库：`go build ./... && go vet ./... && go test -count=1 ./...`，10 个包全绿；
  `internal/adminclient/adminclient_test.go` 用真实 `api.Server`（httptest）跑
  「构建清单 → PlanAssets → Import → 落库 → 验签 BOM」，并验证重跑只跳过、错误码映射。
- 生产 `https://app.syntropy-lab.com`（2026-10-09）：重置生产库后灌入 0.4.3，
  `product` 17 件 + `codex` 4 件 + `node-runtime` 5 件 = **26 件制品**（blobs 约 2.4 GB），
  BOM 发布在 `stable` 渠道；`/v1/manifest` 返回 `0.4.3` 与 desktop 槽位安装器；
  同一份发布包重跑**全部 skipped**、release 复用。
- 真实决策链路：对生产服务 `POST /v1/plan`（上报 product 0.4.2 / codex 0.159.0 /
  node-runtime 24.13.0 / templates 0.0.1）返回三条 `upgrade`（product → 0.4.3、codex → 0.160.0、
  node-runtime → 24.14.0，产品只占**一行**，5 个槽位由客户端展开）加 templates 一条明确 `skip`
  （`渠道缺少可用发布`）；blob 支持 Range 取件（206）、`/v1/pubkey` 200。
- 本地临时服务全链路：导入 → 验签 BOM → 管理页 jsdom 冒烟（`tests/ui/dom-smoke.mjs`）全过。

## 升级注意

- 部署与配置见 `README.md`：`deploy/install.sh` + `deploy/syntropy-update.service`。
- 本版改了制品键与管理面路由，**0.4.3 之前的客户端不能用这套路由**，升级前先确认桌面端版本。
- 生产库本次重置过，备份保留在 `/var/lib/syntropy-update/data.before-seed-*` 与
  `data/*.bak-20261009-162132`；`data/acme/` 保留（ACME 证书缓存，删掉会撞签发限流）。

## 发布方式（本仓库自身的版本怎么出）

1. 写 `docs/releases/vX.Y.Z.md`（就是这份的样子）；
2. 在 `CHANGELOG.md` 的表里加一行；
3. 打 tag：`git tag vX.Y.Z && git push origin main --tags`。
